# UI element taxonomy merge proposal

This proposal merges the [UI element taxonomy](../../docs/ui-element-taxonomy.md#1-input-and-editing-elements)
into the canonical OpenUI taxonomy, so that the file can then be retired, as the project
owner decided (plan question Q4). Every abstract type of that file either already matches
an OpenUI term, or gets one of four actions, or is listed under [Not added](#not-added)
with its reason. It uses the terms approved in the [terminology proposal](terminology.md#summary),
the [taxonomy mapping change](taxonomy_mapping_change.md#summary) and the sections and
subcategories approved in the [category change proposal](category.md#summary).

| Action               | Meaning                                                                                                                                                                                                          |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Change A to B**    | Abstract type A is the same concept as, or a variant of, the existing or approved term B. A merges into B and gets no taxonomy entry of its own.                                                                 |
| **Replace A with B** | Abstract type A covers several concepts. Existing or approved terms B (one or more) take over its content.                                                                                                       |
| **Delete A**         | Abstract type A is removed with no successor, because it is not a UI element the document describes.                                                                                                             |
| **Add C**            | C is a new taxonomy entry for abstract type A, placed under the named scope with the named abstraction level, section and subcategory. Adding a term does not create a new scope or known object type by itself. |

- **Where each change applies:** the canonical
  [taxonomy mapping](../scopes/taxonomy_mapping.md#input-elements) (for Add rows, the named section and subcategory)
  and the same entry in the [generic UI taxonomy](../../docs/generic-ui-taxonomy.md#input-elements).
  Change, Replace and Delete rows add no entry; they record where each abstract type went,
  which the retirement of the file needs.
- **Inputs:** the [UI element taxonomy](../../docs/ui-element-taxonomy.md#1-input-and-editing-elements) with its
  [classification rules](../../docs/ui-element-taxonomy.md#classification-rules); the
  [taxonomy mapping](../scopes/taxonomy_mapping.md#input-elements) (151 entries); the approved
  [terminology](terminology.md#summary), [taxonomy mapping change](taxonomy_mapping_change.md#summary),
  [category](category.md#4-add), [scope](scope_change.md#summary),
  [architecture](architecture_change.md#summary) and [structure](structure_change.md#add)
  proposals; the [glossary](../scopes/scope.md#glossary); and the survey taxonomy mappings they cite.
- **Status:** proposal for review; nothing is applied. It answers W3 task 14.1 in the
  [v1 publish plan](specui_v1_publish_plan.md#w3-ui-categorization). After approval
  (task 14.2) the Add rows are applied in W3 tasks 14.4–14.5, and the appendix records
  where every abstract type went when the file is retired (task 14.6).
- **Naming rule used:** the approved
  [canonical-term rule](terminology.md#appendix-a-canonical-term-rule): keep an OpenUI
  term; otherwise the HTML or WAI-ARIA name; otherwise the name most surveyed frameworks
  share; otherwise a neutral descriptive name. Never a framework class or brand.
- **Count:** the file has 222 abstract type rows with 221 distinct names; Coach Mark
  appears in both category 11 and category 13. The
  [category proposal](category.md#appendix-a-ui-element-taxonomy) gives the same count.

## 0. Already covered

These abstract types already match a taxonomy entry, a scope object named in the
taxonomy mapping, an approved term or a glossary term or alias. No action is needed.

Matching method, applied in order; a type is listed here at the first step that matches:

1. **Same name:** the type's name equals the term, ignoring case, hyphens and a plural.
2. **Glossary alias:** the type's name, or its purpose, is an alias or named variant in
   the glossary entry of the term (for example submit button under Button).
3. **Typical element:** one of the type's own typical concrete elements is the term, and
   the type's purpose is that term's purpose (for example Text Input, whose typical
   element is Text field).
4. **Same concept:** the type names the term's concept with a common synonym, and the
   term's definition says so (for example Determinate Progress and Progress mode).

A type whose only match is a related, not identical, concept is not listed here; it gets
a Change or Replace row.

### Not added

None of these abstract types gets a taxonomy entry.

- **Accessibility and alternative interaction** (category 15, all ten types): none of them is
  a UI element. Each is a property of another element or a part that an existing or approved
  term already covers, so none is added, whatever plan question Q13 decides about
  accessibility scopes. What covers each one:
  - **Focus Indicator:** The approved Focus outline already covers how focus is drawn.
  - **Skip Control:** Its visible part is a Link to the main Region.
  - **Accessibility Label:** An accessible name is a property of every element, not an element.
  - **Description:** An accessible description is a property of an element, not an element.
  - **Live Region:** The approved Narration covers announcing changes; the OpenUI5 review maps `sap.ui.core.InvisibleMessage` there.
  - **Landmark:** The regions themselves are the existing Region and Navigation bar entries.
  - **Keyboard Alternative:** Keyboard shortcuts and access keys are Interaction definitions.
  - **Gesture Alternative:** The alternative controls are Buttons.
  - **Caption or Transcript:** Captions (Add row) and Text cover the visible parts.
  - **Error Association:** The error text itself is part of the Form field.
- **Voice Input** (category 1): Speech entry is a platform service, not a UI element the document describes, for the same reason terminology Delete D1 removed Biometric prompt. A dictation button is a Button.
- **Transfer Selection** (category 2): No surveyed standard or framework offers a transfer list as a control. It is built from two list boxes and buttons.
- **Duration Selection** (category 2): No surveyed standard or framework offers a duration control; HTML has no duration input.
- **Repeating Action** (category 3): Repeating while pressed is a capability of a button (Qt `autoRepeat`), not an element type. Any attribute for it belongs to the Action controls contract in W6 task 25.
- **Index Navigation** (category 4): No surveyed standard or framework offers an index or A to Z rail as a control.
- **Preview** (category 5): No surveyed standard or framework offers a general preview control. A preview is shown with an Image, a Media player or a Dialog.
- **Immersive View** (category 6): No surveyed standard or framework offers panoramic, AR or VR views; they need device interfaces outside the surveyed sources.
- **Query Builder** (category 12): No surveyed standard or framework offers a general rule builder as a control. Conditions for one field are part of Value help.
- **Saved Query** (category 12): No surveyed library has a saved search control. Storing criteria is application data, not a UI element.
- **Walkthrough** (category 13): No surveyed standard or framework offers a product tour. Its steps are Popovers.
- **Permission Request** (category 14): A permission prompt is shown by the browser or platform, not by the application, for the same reason terminology Delete D1 removed Biometric prompt.

## 5. Classification rules

Nothing new is needed. The approved changes already define every
[classification rule](../../docs/ui-element-taxonomy.md#classification-rules) of the UI element
taxonomy; the right column names where. W3 task 14.3 writes them into the
[taxonomy mapping](../scopes/taxonomy_mapping.md#input-elements).

| Rule in the UI element taxonomy                                                                                                                                                                                                 | Inclusion rule in the taxonomy mapping                                                                                                                                                                                |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Classify an element by its primary purpose in its current context.                                                                                                                                                              | Each taxonomy entry belongs to exactly one section and at most one subcategory, chosen by its primary purpose. This is the check of W3 task 14.7.                                                                     |
| An element may have secondary roles.                                                                                                                                                                                            | Secondary roles go in the entry's note, not in a second row; the [taxonomy mapping change](taxonomy_mapping_change.md#kept) keeps one spec object per row.                                                            |
| Hover states, touch targets, gestures, mouse events and keyboard events are not element types; they belong to a companion taxonomy of interaction definitions (states, target properties, gestures, input events and commands). | They are the Interaction definitions section, whose four subheadings become the subcategories Interaction states, Interaction areas and constraints, Gestures and Input events ([category C6](category.md#1-change)). |
| Each "Holds" line of the approved subcategories                                                                                                                                                                                 | Becomes the inclusion rule of that subcategory ([category: Add](category.md#4-add)).                                                                                                                                  |
