# Behavior capability mapping

Status: Steps 9–11 completed as research, mapping and an unmerged proposal. No canonical scope has been adopted or changed. “New leaf” and “enhance” below are proposal dispositions, not approval. Evidence is the fixed-baseline [Step 8 inventory](BEHAVIORS.survey.md); each B-reference links to the research section containing its exact row and pinned sources.

## Representation and decision rules

Evaluate reuse, enhancement, a new leaf, a coherent subcategory, then a new top-level category. A research grouping does not automatically become a canonical folder. Existing taxonomy abstraction levels retain their definitions; the disposition column below records a separate merge decision.

- A **Behavior scope object** models a reusable capability applied to a host. Three new candidates are staged here.
- A **Behaves attribute** invokes an action on its host, such as Table sorting or Expandable panels expansion. It is not a declaration of a new Behavior type.
- A **Uses attribute** supplies state/configuration/references; a **Produces attribute** reports an event. A close request does not prove closure, and a sort-state notification does not prove sorted rows.
- **Interaction, Layout and Presentation** retain state/event vocabulary, geometry and styling mechanisms. They are not replaced by a new Behavior leaf for each observed implementation detail.

## Required distinctions for future merge

- **Collapsible:** existing target entries cover only pages/views. AM-E10 proposes additive container/widget applicability; AM-E13 keeps the panel as the expanded-state owner. Recursive tree operations and exclusive accordion coordination remain host policy.
- **Resizable:** existing user-driven resizing is not evidenced by automatic textarea fitting, dynamic tab height, grid sizing or a passive divider. No amendment is proposed here.
- **Drag and drop:** its current applicability already covers container/widget hosts. B39 supplies contextual table integration evidence only; no new fields or default dragging are added.
- **Qt Scroll container:** a proposed object owns viewport/content; Scrollable targets that object or an existing content region. Scrollbar visibility is not the same as scrolling being enabled. Accept neither proposal's fields by reference alone.
- **Qt Text completion:** reuse its pending draft for later joint review instead of adding another TextCompletion type. Material evidence supports popup candidates and consumer filtering; it does not approve inline completion or string-only candidate contracts.
