This is a secondary capability view of the existing [inventory](INVENTORY.md), not a new primary classification. Material sources were read from the previously verified cache and their Git blob hashes rechecked. Tests below were read as upstream expectations, not executed.

The canonical [scope rules](../../../scopes/scope.md), [leaf template](../../../scopes/template.scope.md), [taxonomy mapping](../../../scopes/taxonomy_mapping.md), [evidence register](../../../scopes/evidence.md), existing [Behaviors](../../../scopes/Behaviors/scope.md) leaves, and the [object crosswalk](TAXONOMY_MAPPING.md) were reviewed before extracting candidates. Framework examples support research; they do not authorize neutral contracts by themselves.

The unit of research is an evidenced capability on a named host or directive. Each row separates observed implementation/documentation from candidate interpretation and limitations. A shared source can support several capabilities; primary file/folder/export ownership is unchanged. Capability IDs are local research references, not proposed canonical identifiers.

For this pass, **object** means the host being studied; **capability** means what it can do; **configuration** selects a policy or state; **event** reports an occurrence; **styling** determines presentation. These are working distinctions referencing the existing glossary, not competing formal definitions. A capability may ultimately remain a host contract, interaction notion, layout policy or supporting mechanism instead of becoming a standalone Behavior.

## Bounded calibration and verdict

The initial sample comprised Dialog, Bottom sheet, Sidenav, Expansion, Tabs and Table. Relevant overviews, configuration/runtime files, styles and upstream test expectations were inspected before extending the same method to the remaining families.

- **Dialog:** the host contains a scrollable content region; opening/closing, initial focus, trapping/restoration, backdrop dismissal and page scroll locking are separate responsibilities. Height constraints and overflow rules are corroborated by the documented content role, not inferred from CSS alone.
- **Bottom sheet:** bottom-edge placement does not define modality. Shared focus/dismissal behavior and page scroll blocking coexist with an independently evidenced single-sheet replacement policy.
- **Sidenav:** layout mode supplies default backdrops; actual focus trapping follows open state and the currently visible backdrop. Initial auto-focus is separate. A scrollable content host does not prove global background scroll locking.
- **Expansion:** a header triggers disclosure, configuration controls eligibility, expanded state and completion events differ, and animation styling is not the capability itself. Disabled user activation can differ from programmatic state changes.
- **Tabs:** body scrolling and header overflow navigation are distinct, and dynamic-height mode changes overflow styling. A test asserts scrollable registration, not that every layout actually overflows.
- **Table:** the table does not automatically own an overflow viewport. The pinned overview explicitly describes optional CDK virtual-viewport composition with consumer styling, and independently describes sticky regions and optional drag/drop integration.

**Verdict: viable.** The sample distinguishes objects, capabilities, configuration, events and styling, so the research method was applied across all 39 family subcategories and the direct package artifacts. It does not establish runtime correctness or that every candidate merits a scope extension. The completed Step 9 [mapping](BEHAVIOR_MAPPING.md) evaluates canonical destinations and structural gaps.

## Research grouping definitions

- **Direct objects:** attachable Material directives already exposing a reusable response or coordination surface, without asserting that their Angular APIs should become neutral scope types.
- **Modal interaction and surface lifecycle:** opening/closing, focus coordination, dismissal, isolation and replacement.
- **Scrolling and viewport response:** internal scrolling, scroll observation, page locking, anchored-surface repositioning, clipping response and viewport-dependent rendering.
- **Disclosure and content activation:** reveal/hide content, coordinate active regions and control when content is created or retained.
- **Selection and value manipulation:** coordinate choices and value changes, including request-versus-commit boundaries.
- **Data operations and completion:** request paging/ordering or present suggestions, separate from processing and retrieval.
- **Feedback and interaction policy:** availability, transient feedback, description/announcement and progress-state exposure.
- **Field coordination and automatic sizing:** associate controls with feedback and fit content automatically.
- **Contextual integrations requiring explicit boundaries:** optional dependency-level patterns whose Material integration evidence must not be mistaken for a built-in default.

## Findings and unresolved interpretation

1. **Modality is composite.** Opening a surface, intercepting background interaction, containing/restoring focus, and blocking page scrolling are separate observed responsibilities. `hasBackdrop`, `autoFocus`, `disableClose`, `ariaModal` and scroll strategies configure different aspects. In particular, Material Dialog defaults `ariaModal` to false while still providing modal interaction patterns; copying it as the neutral modality switch would be wrong.
2. **Scrolling has several meanings.** Internal overflow (B09–B11), revealing a header item (B12), global page locking (B13), repositioning (B14), clipping dismissal (B15), virtual rendering (B16), stickiness (B17) and contextual close-on-scroll (B40) must remain distinguishable. A wheel/scroll event or a scrollbar control does not establish all of them.
3. **Focus evidence needs configuration qualifiers.** Drawer documentation describes typical mode defaults, while runtime/tests additionally cover explicit backdrop overrides. Dialog overview uses `first-header` in its focus-target table, whereas its configuration type uses `first-heading`; use the pinned declaration for the accepted API spelling and do not propagate either spelling as a neutral spec key.
4. **Event names do not prove data mutation.** Chip removal and paging/sorting requests may require consumer handling. Toggle attempts can differ from value changes. Step 9 must preserve these distinctions when evaluating Produces, Behaves and reusable behavior objects.
5. **Integration is not a built-in capability.** Table drag/drop and virtual scrolling, plus textarea autosizing, depend on explicitly described CDK composition. Slider dragging is not object drag/drop, and automatic text sizing is not user-operated resizing.
6. **Evidence strength varies.** Some tests assert focus, state or registration rather than geometric scrolling. Form-field evidence uses integration and harness tests. Table/CDK composition has documentation/delegation evidence without a complete dependency test review. B39 and B40 intentionally retain narrower, contextual status.
7. **Canonical structure remains undecided.** No new Behavior, category or subcategory is adopted here. The current Collapsible/Resizable target model covers pages/views, while Drag and drop also names containers/widgets. Their proposed applicability, ownership, groupings and cross-survey reconciliation are now recorded in [BEHAVIOR_MAPPING.md](BEHAVIOR_MAPPING.md) and [SCOPE_EXTENSION_PROPOSAL.md](SCOPE_EXTENSION_PROPOSAL.md); they remain unapproved.
