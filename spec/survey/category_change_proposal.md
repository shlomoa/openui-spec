# Consolidated category change proposal

This proposal turns the category findings of the four UI surveys into concrete changes to
the OpenUI taxonomy categories. It uses the terms approved in the
[terminology proposal](terminology_proposal.md#decisions-needed). Each recommendation is
one of four actions on a specific category or subcategory.

| Action               | Meaning                                                                                                                                     |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **Change A to B**    | Same category, new name or heading level.                                                                                                   |
| **Replace A with B** | A is removed and a different category or several subcategories B take over its content.                                                     |
| **Delete A**         | A is removed with no successor.                                                                                                             |
| **Add C**            | C is a new category or subcategory, with the taxonomy entries it holds. Adding a category does not create a new scope or known object type. |

- **Categories in OpenUI:** the taxonomy sections, such as Input elements or Output
  elements. A **subcategory** is a group of taxonomy entries inside one section. Each
  taxonomy entry keeps its scope and abstraction level; a subcategory only groups entries
  for reading.
- **Where each change applies:** the section headings of the
  [generic UI taxonomy](../../docs/generic-ui-taxonomy.md#input-elements) and of the canonical
  [taxonomy mapping](../scopes/taxonomy_mapping.md#input-elements). In both files a section
  is a level-2 heading and a subcategory is a level-3 heading; in the taxonomy mapping each
  subcategory gets its own table.
- **Inputs:** the category file of each survey
  ([Angular Material](angular-material/category.md#categories),
  [HTML Standard](html5/category.md#categories), [OpenUI5](openui5/category.md#categories),
  [Qt Widgets](qt/category.md#categories)), their architecture proposals, and the Qt
  [proposed extension tree](qt/inventory/TAXONOMY_STRUCTURE_PROPOSAL.md#proposed-extension-tree),
  the only survey output that proposes taxonomy subcategories.
- **Status:** proposal for review. Nothing is applied. It feeds plan question Q4, scope
  workstream W3 task 13 and terminology step 9.3 in the
  [v1 publish plan](specui_v1_publish_plan.md#plan-completion).
- **Naming rule used:** the approved [canonical-term rule](terminology_proposal.md#appendix-a-canonical-term-rule),
  applied to category names: keep an existing OpenUI name; otherwise use the Qt survey's
  neutral grouping name. Framework category names never become OpenUI categories.
- **Terms:** member lists use only existing taxonomy entries and terms approved in the
  terminology proposal. Terms in **bold** are new or renamed by that proposal.

## 4. Add

Each subcategory lists every taxonomy entry it holds, so each entry of the four element
sections belongs to exactly one subcategory. Layout and structural elements stays one
flat list of twelve entries, because only the Qt survey proposes a grouping there: Grid,
Pane, Rail, Stack, Scaffold, Region, Splitter, **Bar**, **Page stack**, **Scroll container**,
**Splitter handle** and **Flexible column layout**.

  assistance, Choice coordination and Content motion: replaced by the Behaviors section
  (A1) and its two new scopes.

  State indicators:** Layout and structural elements stays flat, and the existing
  subheadings of the other sections already hold these terms (4.6).
