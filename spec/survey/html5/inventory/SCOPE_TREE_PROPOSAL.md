# Proposed scope-tree extensions and merge plan

Status: proposal for review, 2026-09-23. This document records proposed changes; it does not change the canonical scope tree or authorize new contract fields. The user's request is to map and propose a future merge. The supplied documents describe the current model and are not separate instructions to perform that merge.

## Recommendation

Keep the eleven existing top-level scopes and their current identities. Enrich the existing control, container, and widget families first. Add a small number of missing contracts where the HTML evidence identifies a distinct responsibility. Consider two cross-cutting folders, Accessibility and Composition, after deciding their boundaries. Do not mirror the HTML specification chapters under `scopes/`: browser parsing, scheduling, storage, and worker machinery are implementation dependencies rather than UI taxonomy objects.

The [151-entry taxonomy crosswalk](TAXONOMY_MAPPING.md) preserves current aliases and target paths. The [118-section source crosswalk](SURVEY_SCOPE_CROSSWALK.md) records where HTML research can contribute and where it cannot. Both are family/section mappings; neither claims a completed semantic review of every inventoried definition.

## Tree shape and restructuring alternatives

The recommended additive shape retains Application, Controls, Behaviors, Pages, Views, Containers, Widgets, Layout, Presentation, Internationalization, and Interaction. P1–P5 and P8 add leaves within those folders only if their contract gaps survive review. P6 and P7 would be additional top-level notion folders.

1. **Enrich in place — recommended first.** Preserve every existing leaf path, scope id, instance id, and instance type. Add supported fields/children or clarify prose and evidence. This minimizes migration and reveals whether new leaves are actually needed.
2. **Split broad families selectively.** If divergent variants cannot be described coherently, introduce a family folder with distinct child contracts. Candidate families are ChoiceControls, DisplayPrimitives, and DrawingAndCapture. First design an explicit old-path/new-path and id/type migration map. A folder plus a same-named retained leaf can derive colliding ids; folder conversion is not a filesystem-only move.
3. **Replace the tree with HTML chapters — reject.** It would mix controls with parsing, workers, and browser algorithms; fragment cross-cutting Interaction/Presentation concepts; and turn a technology-neutral UI model into an HTML implementation catalog.

Before any move, inventory consumers of `scopeDocument`, generated ids/types, taxonomy links, the evidence register, documentation navigation, fixtures, and generator mappings. Preserve existing identities when possible; if an identity must change, document the exact migration and version impact. Alias labels do not themselves preserve literal type compatibility.

## Template and evidence-register proposals

Keep the template's existing three machine-bearing sections and their line patterns. During a later documentation update, clarify these points in prose rather than changing the converter grammar:

- Identity type is the chosen semantic category, not an automatic copy of an HTML tag/interface or a taxonomy alias.
- Attributes distinguish author configuration, produced events, and abstract actions. A DOM method is evidence for behavior, not automatically a child object. A readonly platform property is not automatically an input.
- Variant-specific attribute applicability belongs in validation prose unless an explicit schema/converter change is proposed. Do not imply constraints, value types, or multiplicity are fully enforced merely because prose describes them.
- Child model enumerates owned content. Form association, focus targets, event payloads, browser collections, and dependency references require separate ownership decisions.
- Accessibility and Validation notes may link to the proposed cross-cutting notions without re-enumerating the machine-bearing fields.
- Each leaf should link to its entry in the existing evidence register. Keep one row per leaf, but make the Source/Citation cells contain precise snapshot links and make Authorizes distinguish HTML facts, approved OpenUI abstraction, and framework example.

The evidence register's current family entries often authorize purpose and alias grouping only. The proposed HTML crosswalk supplies candidate evidence; it does not retroactively approve all implementation-derived attributes described by those families. For folders such as Interaction, maintain notion-level source links in `scope.md` or propose a separate folder-evidence section rather than fabricating leaf entries.

## Future merge sequence

1. **M1 — Freeze and reconcile inputs.** Compare the four file fingerprints in the crosswalk with the current files. Review TM entries and P1–P8, record accepted/rejected/deferred dispositions, and resolve obsolete-feature treatment without reinstating removed plan step 1.4.
2. **M2 — Review candidate evidence.** Confirm each selected HTML section and identify exactly which attributes, actions, children, or prose claims it supports. Split platform facts from OpenUI decisions. Obtain external sources for accessibility patterns, gestures, layout, capture, and composite widgets where needed.
3. **M3 — Select the smallest contract change.** Prefer enrichment or composition of current known types. For each accepted new leaf/folder, record its parent, purpose, stable identity plan, ownership model, and the old/new mapping if anything moves.
4. **M4 — Author scope changes and traceability together.** Use the unchanged leaf template, update folder indexes, update existing taxonomy rows without creating duplicate aliases, and amend exactly one evidence-register row per affected leaf. Include precise proposed-to-accepted decision references.
5. **M5 — Regenerate and inspect the catalog.** Use the existing `spec/to_json` converter; do not hand-edit `spec/openui.json`. Review the exact added/removed ids and literal types, child ownership, duplicate identities, string-or-null attributes, and changes to `scopeDocument` paths. Treat new folder types as catalog changes too.
6. **M6 — Validate and document migration.** Run the applicable converter/spec contract tests, known-type checks, link/Markdown checks, and repository documentation checks from the local environment. Update affected fixtures/generator mappings only where the accepted change requires them. Publish the old/new identity map for any breaking change.

Detailed execution should follow the repository's [contribution validation workflow](../../../../CONTRIBUTING.md) and [converter source contract](../../../README.md#leaf-scope-source-format-scope-md). This request produces the reviewable mapping and proposal; it does not perform M1–M6 or mark the full survey's steps 4–7 complete.

## Acceptance criteria for the eventual merge

- Every selected survey item has one semantic owner plus explicit cross-references, or a recorded deferred/external disposition.
- All current taxonomy entries remain accounted for; alias names are not silently promoted to new instance types.
- Every changed/new leaf follows the template and has one precise evidence-register entry.
- HTML facts, OpenUI abstraction decisions, and framework reference patterns remain distinguishable.
- The regenerated catalog is deterministic, identities are unique, and all changed literal types and paths have been reviewed for compatibility.
- Attribute applicability and owned children are justified independently of visual similarity or HTML chapter placement.
- Unmerged items retain their survey status; a category mapping does not claim completed object-level research.
